# QuickNotes Data Model

QuickNotes stores four entities: **users**, **notes**, **tags** and **note_tags**. The SQL below is written for PostgreSQL.

## Entities

### users

| Column | Type | Key / constraint | Description |
|---|---|---|---|
| id | BIGSERIAL | **Primary key** | Unique user id, generated by the database |
| email | VARCHAR(255) | NOT NULL, UNIQUE | Login email; two accounts cannot share one |
| password_hash | VARCHAR(255) | NOT NULL | Hashed password (for example bcrypt); the real password is never stored |
| display_name | VARCHAR(100) | NOT NULL | Name shown in the app |
| created_at | TIMESTAMPTZ | NOT NULL, default now() | When the account was created |

### notes

| Column | Type | Key / constraint | Description |
|---|---|---|---|
| id | BIGSERIAL | **Primary key** | Unique note id |
| user_id | BIGINT | **Foreign key → users.id**, NOT NULL | Owner of the note |
| title | VARCHAR(100) | NOT NULL, not empty | Note title (max 100 characters, matching the API) |
| body | TEXT | NULL allowed | Note content (optional) |
| created_at | TIMESTAMPTZ | NOT NULL, default now() | When the note was created |
| updated_at | TIMESTAMPTZ | NOT NULL, default now() | When the note was last changed |

### tags

| Column | Type | Key / constraint | Description |
|---|---|---|---|
| id | BIGSERIAL | **Primary key** | Unique tag id |
| user_id | BIGINT | **Foreign key → users.id**, NOT NULL | Owner of the tag (each user has their own tags) |
| name | VARCHAR(50) | NOT NULL, UNIQUE together with user_id | Tag name, for example "work" |
| created_at | TIMESTAMPTZ | NOT NULL, default now() | When the tag was created |

### note_tags

| Column | Type | Key / constraint | Description |
|---|---|---|---|
| note_id | BIGINT | **Foreign key → notes.id**, part of the primary key | The tagged note |
| tag_id | BIGINT | **Foreign key → tags.id**, part of the primary key | The tag applied to it |

The primary key of note_tags is the pair **(note_id, tag_id)**. This is a composite key: the same tag cannot be attached to the same note twice.

## Relationships

```text
 ┌───────┐ 1      N ┌───────┐ 1      N ┌───────────┐ N      1 ┌──────┐
 │ users │─────────<│ notes │─────────<│ note_tags │>─────────│ tags │
 └───┬───┘          └───────┘          └───────────┘          └──┬───┘
     │ 1                                                         │ N
     └───────────────────────────────────────────────────────────┘
       one user owns many tags          ("<" and ">" point to the "many" side)
```

- **users → notes is one-to-many.** One user can write many notes, but each note belongs to exactly one user. This is stored with the foreign key `notes.user_id`.
- **users → tags is one-to-many.** One user has many tags, and each tag belongs to one user. Two users can both have a tag called "work" without sharing it.
- **notes ↔ tags is many-to-many.** One note can have many tags ("work", "urgent"), and one tag can be on many notes. A relational database cannot store a list inside one column, so the **join table** `note_tags` holds one row for every note–tag pair. It turns one many-to-many relationship into two one-to-many relationships (notes → note_tags and tags → note_tags).

**Deleting:** `ON DELETE CASCADE` means that deleting a user deletes their notes and tags, and deleting a note or tag deletes its rows in note_tags. The notes themselves are never deleted when only a tag is removed.

## CREATE TABLE statements

```sql
CREATE TABLE users (
    id            BIGSERIAL    PRIMARY KEY,
    email         VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    display_name  VARCHAR(100) NOT NULL,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE notes (
    id         BIGSERIAL    PRIMARY KEY,
    user_id    BIGINT       NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title      VARCHAR(100) NOT NULL CHECK (length(trim(title)) > 0),
    body       TEXT,
    created_at TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE tags (
    id         BIGSERIAL   PRIMARY KEY,
    user_id    BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    name       VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id, name)
);

CREATE TABLE note_tags (
    note_id BIGINT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
    tag_id  BIGINT NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    PRIMARY KEY (note_id, tag_id)
);
```

## Example queries

**1. List a user's 20 newest notes (used by `GET /notes`)**

```sql
SELECT id, title, body, created_at, updated_at
FROM notes
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;
```

**2. Find all of a user's notes with the tag "work" (JOIN, used by `GET /notes?tag=work`)**

```sql
SELECT n.id, n.title, n.created_at
FROM notes AS n
JOIN note_tags AS nt ON nt.note_id = n.id
JOIN tags      AS t  ON t.id = nt.tag_id
WHERE n.user_id = 1
  AND t.name = 'work'
ORDER BY n.created_at DESC;
```

**3. Count how many notes use each of a user's tags (used by `GET /tags`)**

```sql
SELECT t.id, t.name, COUNT(nt.note_id) AS note_count
FROM tags AS t
LEFT JOIN note_tags AS nt ON nt.tag_id = t.id
WHERE t.user_id = 1
GROUP BY t.id, t.name
ORDER BY t.name;
```

`LEFT JOIN` keeps tags that are not used by any note, so they appear with a count of 0.

**4. Create a note and attach a tag in one transaction (used by `POST /notes`)**

```sql
BEGIN;

INSERT INTO notes (user_id, title, body)
VALUES (1, 'Shopping list', 'Milk, eggs, bread')
RETURNING id;                       -- returns, for example, 42

INSERT INTO note_tags (note_id, tag_id)
VALUES (42, 7);                     -- 7 is the id of the user's "home" tag

COMMIT;
```

The transaction makes sure the note and its tags are saved together, or not at all.

## Indexes

```sql
CREATE INDEX idx_notes_user_created ON notes (user_id, created_at DESC);
CREATE INDEX idx_note_tags_tag_id   ON note_tags (tag_id);
```

- **`idx_notes_user_created`** is the most important index. `GET /notes` is the most frequent request (about 40 per second on average), and it always filters by `user_id` and sorts by `created_at`. Without the index, the database would have to scan every note in the table, about a million new rows per day, to find one user's notes. With it, the database jumps straight to that user's notes, already in newest-first order. This is what makes a cache miss take about 5–20 ms instead of seconds.
- **`idx_note_tags_tag_id`** helps query 2 and query 3. The primary key `(note_id, tag_id)` already makes lookups by `note_id` fast, but not lookups that start from a tag, because `tag_id` is the second column of that key.

The `UNIQUE` constraints on `users.email` and `tags (user_id, name)` create indexes automatically, which also makes login by email fast.

**The cost of indexes:** each index uses disk space and makes every insert slightly slower, because the index must be updated too. QuickNotes has about 4× more reads than writes, so these two indexes are worth it. We do not index columns we never search by, such as `body`.

## SQL or NoSQL?

QuickNotes uses a **relational SQL database (PostgreSQL)**. The data is clearly structured and connected: users own notes and tags, and notes and tags have a many-to-many relationship, which SQL handles naturally with foreign keys, a join table and JOIN queries. Foreign keys and transactions protect correctness, so a note can never point to a user that does not exist, and a note and its tags are saved together. The scale also fits: the load estimate is about 200 reads per second at peak and about 180 GB of new notes per year, which one well-indexed PostgreSQL primary with read replicas can handle comfortably. A NoSQL document store would be a reasonable choice if notes became huge, unstructured documents or if we needed to spread data across many machines from the start, but it would make tag queries and consistency harder, so it would add complexity without solving a problem we have today.
